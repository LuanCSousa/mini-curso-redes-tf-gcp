Módulo 05 • Diagnóstico de Rede Resolvendo o Suspense das 11h50

Por que o ping 8.8.8.8 deu 100% packet loss na nossa VM?

1 Olhando a Tabela de Rotas da VPC

Toda VPC no Google Cloud já nasce com 2 rotas automáticas na tabela de roteamento:

Destino (Destination) Próximo Salto (Next Hop) Para que serve?
10.<ID>.0.0/24 Virtual Network (Local) Entrega pacotes entre VMs da mesma sub-rede.
0.0.0.0/0 Default Internet Gateway Qualquer IP fora da VPC é enviado para o gateway de internet!
2 Se a rota 0.0.0.0/0 existe, por que falhou?
  • Endereços Privados (RFC 1918) não navegam na Internet Pública: Nossa VM tem apenas o IP privado 10.<ID>.0.2.
  • Se um pacote saísse para o 8.8.8.8 com IP de origem 10.7.0.2, o servidor do Google DNS não saberia para qual das milhões de redes 10.x.x.x do mundo devolver a resposta!
  • Por isso, o Default Internet Gateway descarta pacotes de VMs sem IP externo... a menos que exista um tradutor NAT no caminho!
Módulo 05 • Fundamentos Clássicos O Mesmíssimo Conceito do Wi-Fi da Sua Casa

Como o SNAT (Source NAT) traduz IPs privados na saída

1 Pacote Saindo da VM

A VM privada cria um pacote para atualizar o Linux ou dar ping:

Origem : 10.7.0.2:49152
Destino: 8.8.8.8:53

Esse pacote chega até a borda da VPC procurando saída pela rota 0.0.0.0/0.

2 A Tradução no Cloud NAT

O Cloud NAT troca o IP privado da VM por um IP Público compartilhado e anota na tabela interna:

Origem : 34.122.10.55:61001
Destino: 8.8.8.8:53

Agora o pacote tem um IP público real e viaja pela internet!

3 Retorno Seguro (Unidirecional)

Quando o 8.8.8.8 responde para 34.122.10.55:61001, o Cloud NAT consulta sua tabela e devolve para 10.7.0.2.

Segurança Máxima: Ninguém na internet consegue iniciar uma conexão de fora para dentro pelo Cloud NAT!

Módulo 05 • Arquitetura GCP Por que precisamos de 2 recursos no Terraform?

Dupla Dinâmica: Cloud Router + Cloud NAT

CR 1. Cloud Router (google_compute_router)

É o Plano de Controle Regional da rede. Em cenários híbridos (VPN / Dedicated Interconnect), ele fala o protocolo BGP.

Para o Cloud NAT, o Cloud Router atua como o "cérebro organizador" onde penduramos a configuração de tradução de endereços daquela região.

NAT 2. Cloud NAT (google_compute_router_nat)

É o Serviço de Tradução Definido por Software na Andromeda:

  • nat_ip_allocate_option = "AUTO_ONLY": O próprio GCP aloca e gerencia os IPs públicos de saída automaticamente.
  • source_subnetwork_ip_ranges_to_nat = "ALL_SUBNETWORKS_ALL_IP_RANGES": Qualquer VM privada em qualquer sub-rede da região ganha saída para a internet na hora!

resource "google_compute_router" "router_aluno" {
  name    = "router-${var.region}-${local.student_suffix}"

  source_subnetwork_ip_ranges_to_nat = "ALL_SUBNETWORKS_ALL_IP_RANGES"

  log_config {
    enable = true
    filter = "ERRORS_ONLY"
  }
}
Módulo 06 • Arquitetura Corporativa Conectando Múltiplas Redes

Como conectar duas VPCs no Google Cloud? (Comparativo)

Tecnologia GCP Como Funciona Latência / Banda Quando Usar na Vida Real?
VPC Network Peering
(Nosso Lab 04!)		 Troca direta de tabelas de rotas na SDN Andromeda entre duas VPCs (mesmo em projetos/orgs diferentes). Latência zero adicional (velocidade de linha da VPC). Arquiteturas Hub-and-Spoke, integração entre sistemas internos ou SaaS na nuvem.
Cloud VPN (HA VPN) Túnel criptografado IPsec + roteamento dinâmico BGP via Cloud Router. Até 3 Gbps por túnel (adiciona overhead IPsec). Conectar seu Datacenter On-Premises / Escritório ou outra nuvem (AWS/Azure) ao GCP.
Shared VPC Um projeto "Host" centraliza a VPC e compartilha sub-redes específicas com projetos "Service". Velocidade nativa (é a mesma VPC). Grandes empresas com um time central de Redes/SecOps dentro da mesma Organização GCP.
Private Service Connect Publica apenas 1 serviço específico (via Load Balancer + NAT interno) sem abrir a rede toda. Alta performance unidirecional. Expor uma API privada para clientes/parceiros mesmo quando há conflito de CIDR!
Módulo 06 • Regras de Ouro Fundamentos de VPC Peering

As 3 Leis Inquebráveis do VPC Network Peering

01 Zero Sobreposição de IPs

Duas redes em Peering jamais podem ter sub-redes com o mesmo CIDR.

É exatamente por isso que planejamos no Pré-material cada aluno com 10.<ID>.0.0/24 e o Hub com 10.0.1.0/24 e 10.0.2.0/24!

02 Acordo Bilateral

Ninguém "invade" a VPC do vizinho unilateralmente.

O Peering fica em estado INACTIVE até que a VPC A aponte para a VPC B e a VPC B aponte de volta para a VPC A, mudando o status para ACTIVE!

03 Não-Transitividade

No VPC Peering, "o amigo do meu amigo NÃO é meu amigo"!

O Aluno 01 enxerga o Hub e o Aluno 02 enxerga o Hub, mas o Aluno 01 não consegue pingar o Aluno 02 diretamente. Suas redes continuam isoladas entre si!

Módulo 06 • Engenharia de Limites (Quotas) Como Suportamos 40 Alunos Simultâneos

Arquitetura do Hub Central: Cotas do GCP e Auto-Aceitação

25 Limite Real do GCP: 25 Peerings por VPC

O Google Cloud impõe uma cota padrão de 25 peerings ativos por rede VPC. Para suportar até 40 alunos na sala sem depender de aprovação manual de suporte, aplicamos Sharding de VPC no Hub:

  • Alunos 01 a 20: Conectam na vpc-hub-turma-a (10.0.1.0/24 → Coletor 10.0.1.10).
  • Alunos 21 a 40: Conectam na vpc-hub-turma-b (10.0.2.0/24 → Coletor 10.0.2.10).
⚡ Auto-Aceitação via API (Zero Espera!)

Nosso Cloud Run do Mural possui uma Service Account com permissão compute.networks.addPeering no Hub. Assim que seu Terraform solicita o registro, o Hub cria o lado dele automaticamente!

Módulo 07 • Etapa 05 Boas Práticas de Engenharia Cloud

Como organizamos Terraform na vida real? (Modules)

! O Problema em Projetos Reais

Imagine que sua empresa tem 4 ambientes (dev, qa, staging, prod) ou 30 projetos de clientes.

  • Se você copiar e colar vpc.tf, firewall.tf, nat.tf e peering.tf 30 vezes, qualquer melhoria de segurança exige editar 30 pastas manualmente!
  • Falta de padronização de nomes, tags e logs entre equipes.
M A Solução: Módulos do Terraform

Um Módulo é como uma função em programação:

  • Recebe Parâmetros (variables.tf): Ex: nome da VPC, CIDR, região, regras de firewall.
  • Encapsula a Complexidade (main.tf): Cria VPC, Sub-redes, Router e Cloud NAT seguindo os padrões de segurança da empresa.
  • Devolve Valores (outputs.tf): Retorna o vpc_id e subnet_id prontos para outros módulos usarem!
Módulo 07 • Arquitetura Modular terraform/modules/

Os 3 Módulos Padrão do Nosso Repositório

01 modules/vpc-network

Responsabilidade Única: Provisionar a fundação de rede completa e saída para internet.

  • Cria a google_compute_network (Custom).
  • Cria a sub-rede regional com Private Google Access.
  • Configura opcionalmente o Cloud Router + Cloud NAT com um simples booleano enable_nat = true!
02 modules/firewall-rules

Responsabilidade Única: Segurança de perímetro e microsegmentação padronizada.

  • Libera automaticamente SSH via Cloud IAP (35.235.240.0/20) para a tag informada.
  • Libera diagnóstico interno (ICMP) para faixas RFC 1918 autorizadas.
  • Aceita regras customizadas adicionais via mapa.
03 modules/vpc-peering

Responsabilidade Única: Interconexão privada entre redes (Spoke ↔ Hub).

  • Recebe o local_network_self_link e o peer_network_self_link.
  • Padroniza controle de importação/exportação de rotas customizadas.
  • Expõe o estado ativo do Peering nos outputs.

Módulo 07 • Visão de Produção Além da Sala de Aula

O que muda quando levamos esse Terraform para Produção?

01 Remote State no Cloud Storage (GCS)

Em equipe, o arquivo terraform.tfstate nunca fica salvo no notebook do engenheiro.

Usamos um backend "gcs" em um Bucket privado com State Locking (impede que duas pessoas rodem apply ao mesmo tempo) e versionamento ativo!

02 Versionamento de Módulos no Git

Em vez de chamar source = "../../modules/vpc", empresas publicam módulos em repositórios Git com tags semânticas (?ref=v1.2.0).

Assim, o ambiente dev pode testar a v2.0.0 enquanto prod continua estável na v1.2.0.

03 GitOps & CI/CD para Infra

No Pull Request do GitHub/GitLab, uma pipeline roda automaticamente terraform fmt -check, terraform validate, tfsec (segurança) e comenta o resultado do terraform plan para revisão do time!

Módulo 08 • 17h30 – 17h45 FinOps e Ciclo de Vida Completo

Desmontando a Infraestrutura com terraform destroy

$ A Dor de Deletar Recursos no ClickOps

Se você tentar apagar uma VPC pelo Console Web agora, o GCP vai bloquear! Você teria que lembrar de apagar manualmente: primeiro a VM, depois o Peering, depois o Cloud NAT, depois o Cloud Router, depois as regras de Firewall, depois a Sub-rede e só então a VPC.

✓ O Grafo Reverso do terraform destroy

Com 1 único comando, o Terraform lê o grafo de dependências de trás para frente e remove 100% dos recursos na ordem exata, sem deixar nada esquecido gerando fatura!

Terminal — Limpeza Completa (17h30)

# 2. Na pasta terraform/live-coding, destrua os recursos:
