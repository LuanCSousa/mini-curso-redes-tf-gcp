Módulo 01 • Teoria Aplicada Redes Físicas vs. Nuvem

Onde foram parar os cabos, switches e roteadores na Nuvem?

LAN Rede Tradicional (On-Premises)
  • Hardware Dedicado: Switches L2, roteadores L3, appliances físicos de Firewall e cabeamento estruturado.
  • Mudança Lenta e Manual: Criar uma nova VLAN ou alterar uma rota exige acesso via cabo console/SSH em cada equipamento.
  • Ponto Único de Gargalo: Todo o tráfego de saída ou firewall passa por uma "caixa física" central que pode saturar.
  • Escopo Local: Uma LAN fica presa a um prédio ou datacenter; conectar dois estados exige contratar links MPLS/VPN caros.
SDN Google Cloud Andromeda (SDN)
  • Rede Definida por Software: Tabelas de roteamento, sub-redes, NAT e Firewalls são regras de software declaradas via API.
  • Virtualização no Hipervisor: O firewall e o roteamento acontecem direto na placa de rede virtual (vNIC) de cada máquina host, sem "caixa central" de gargalo!
  • Backbone Privado Global: Os datacenters da Google são interligados por cabos submarinos e terrestres próprios.
  • Provisionamento em Segundos: Com 15 linhas de Terraform, criamos uma rede global pronta para produção.
Módulo 01 • Fundamentos IPv4 Desmistificando o CIDR

Entendendo o Bloco 10.<student_id>.0.0/24 na Prática

Um endereço IPv4 possui 32 bits divididos em 4 octetos de 8 bits (cada número vai de 0 a 255). A barra /24 diz quantos bits da esquerda para a direita estão travados para identificar a Rede:

10
00001010 (8 bits)
1º Octeto • Rede Privada (RFC 1918)
<ID>
Aluno 01 a 40 (+8 = 16 bits)
2º Octeto • ID do Aluno
0
00000000 (+8 = 24 bits)
3º Octeto • Sub-rede Principal
0..255
XXXXXXXX (8 bits livres!)
4º Octeto • Hosts (2⁸ = 256 IPs)
Analogia do CEP

Os 24 bits iniciais (10.7.0) são o nome da rua. Os 8 bits finais (.1 a .254) são o número de cada casa (VM) naquela rua.

E se fosse /16?

Em um /16, apenas os 2 primeiros octetos seriam fixos e sobrariam 16 bits para máquinas (2¹⁶ = 65.536 IPs).

E o /32 no Firewall?

Um /32 trava todos os 32 bits (2⁰ = 1 IP). Usamos /32 quando queremos apontar para 1 único IP exato!

Módulo 01 • Pegadinha Clássica de Cloud 256 − 4 = 252 Hosts

Por que nossa primeira VM no GCP recebe o IP .2 e não o .1?

Os 4 Endereços Reservados pelo Google Cloud em toda Sub-rede
Endereço (Ex: Aluno 07) Quem usa? Explicação Técnica
10.7.0.0 Endereço da Rede Identifica a própria sub-rede nas tabelas de roteamento.
10.7.0.1 Default Gateway Virtual Roteador virtual da SDN Andromeda para onde a VM envia pacotes de saída.
10.7.0.2 até .253 IPs Livres (252 hosts) Faixa atribuída às VMs! Por isso sua 1ª VM sempre nasce com final .2!
10.7.0.254 Penúltimo IP (Reservado) Reservado internamente pela Google para serviços da SDN.
10.7.0.255 Endereço de Broadcast Último endereço do bloco /24 segundo o padrão RFC.
Fórmula de Sub-rede no GCP
2(32 − CIDR) − 4

Para uma máscara /24:
2⁸ − 4 = 256 − 4 = 252 IPs utilizáveis.

No Lab 01 vamos exibir o gateway_address no output do Terraform e comprovar que ele é o 10.<ID>.0.1!
Módulo 01 • Arquitetura GCP O Grande Diferencial do Google Cloud

Escopo de Recursos: VPC é Global, Sub-rede é Regional, VM é Zonal

1 VPC Network = Recurso GLOBAL

Uma única VPC no GCP atravessa o planeta inteiro. Ela não tem "região" nem faixa de IP própria: ela é o contêiner global de roteamento e firewall.

2 Subnetwork (Sub-rede) = Recurso REGIONAL

Cada sub-rede vive em uma região geográfica (ex: us-central1 em Iowa ou southamerica-east1 em São Paulo) e possui o bloco CIDR (10.7.0.0/24).

3 Máquina Virtual (VM) = Recurso ZONAL

A VM nasce em um datacenter específico dentro da região (ex: zona us-central1-a), mas consome um IP da sub-rede regional!

Módulo 02 • Infraestrutura como Código O Fim do ClickOps

Por que gerenciar Redes com Terraform em vez do Console Web?

01 O Problema do ClickOps
  • Passos manuais esquecidos ao recriar redes em dev, staging e prod.
  • Regras de firewall temporárias ("só para testar") que ficam abertas para sempre sem documentação.
  • Impossível fazer Code Review (Pull Request) de cliques no navegador.
02 O Poder Declarativo (HCL)
  • Você declara "o estado final que deseja" (ex: quero 1 VPC e 2 regras de firewall), e não o passo a passo imperativo.
  • O Terraform descobre sozinho a ordem de criação (Grafo de Dependências): primeiro a VPC, depois a Sub-rede, depois a VM!
03 O Arquivo de Estado (.tfstate)
  • O terraform.tfstate é a memória do Terraform: ele mapeia cada bloco do seu código .tf para o ID real do recurso criado lá no Google Cloud.
  • No terraform plan, ele compara seu código com o .tfstate e mostra exatamente o que mudará!

Módulo 03 • Etapa 01 Decisão de Arquitetura

Modo Auto vs. Modo Custom: Por que auto_create_subnetworks = false?

✕ VPC em Modo Automático (true)
  • Cria automaticamente 1 sub-rede `/20` em cada uma das +40 regiões do mundo dentro do bloco fixo 10.128.0.0/9.
  • Fatal para VPC Peering: Como todas as VPCs em modo Auto usam exatamente os mesmos IPs (10.128.0.0/20 em us-central1), duas VPCs em modo Auto nunca conseguem fazer Peering entre si!
  • Gera dezenas de sub-redes desnecessárias em regiões onde você nunca vai operar.
✓ VPC em Modo Customizado (false)
  • A VPC nasce 100% limpa, sem nenhuma sub-rede pré-criada.
  • Controle Total de Engenharia: Você escolhe apenas as regiões que vai usar (us-central1) e define seu próprio bloco CIDR planejado (10.<student_id>.0.0/24).
  • Pronta para Interconexão: Garante que não haverá sobreposição de IPs com o Hub Central nem com VPNs on-premises.
  • Habilitamos private_ip_google_access = true na sub-rede para acesso privado às APIs da Google.

Módulo 04 • Etapa 02 Segurança de Rede na Nuvem

Como funciona o Firewall Stateful e as Network Tags no GCP

01 Regras Implícitas da VPC

Toda VPC Custom nasce com 2 regras invisíveis de prioridade máxima (65535):

  • Deny All Ingress: Ninguém entra em nenhuma VM se você não criar uma regra ALLOW explícita.
  • Allow All Egress: As VMs têm permissão para iniciar conexões de saída.
02 O que é "Stateful"?

Em um firewall Stateless (antigo), você precisava liberar a entrada E também a saída da resposta.

No GCP, o firewall é Stateful: ele guarda uma tabela de conexões ativas (*conntrack*). Se o pacote de entrada foi permitido, o pacote de resposta volta automaticamente!

03 Microsegmentação com Tags

Em vez de liberar a porta 22 (SSH) para a VPC inteira, usamos target_tags = ["ssh-iap"] na regra de firewall.

A regra só se aplica às VMs que tiverem a etiqueta tags = ["ssh-iap"] declarada no Terraform!

Módulo 04 • Arquitetura Zero-Trust Sem IP Público, Sem Porta Exposta

Como fazer SSH em uma VM Privada usando Cloud IAP?

! O perigo do IP Público + 0.0.0.0/0 na porta 22

Colocar um IP público numa VM e abrir a porta 22 para 0.0.0.0/0 faz com que ela receba milhares de tentativas de força bruta de bots em poucos minutos.

🔒 A Solução Profissional: Cloud IAP TCP Forwarding
  • Nossa VM nasce sem bloco access_config (sem IP externo!).
  • O Identity-Aware Proxy (IAP) da Google autentica seu usuário via IAM/HTTPS e entrega seu SSH por dentro da rede interna da Google usando o bloco exclusivo 35.235.240.0/20.
  • No Firewall, liberamos a porta 22 apenas para 35.235.240.0/20!

resource "google_compute_firewall" "allow_ssh_iap" {
  name          = "fw-allow-ssh-iap-${local.student_suffix}"
  network       = google_compute_network.vpc_aluno.name
  direction     = "INGRESS"
  source_ranges = ["35.235.240.0/20"]
  target_tags   = ["ssh-iap"]
  allow {
    protocol = "tcp"
    ports    = ["22"]
  }
}

resource "google_compute_instance" "vm_aluno" {

  tags         = ["ssh-iap"]

    initialize_params { image = "debian-cloud/debian-12" }
  }

    subnetwork = google_compute_subnetwork.subnet_principal.id
  }
}
